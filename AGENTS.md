# AGENTS.md

## Shell style

- Keep commands compact, 1-2 lines, with several flags to a line. The one exception is an aws command whose verb is `create-*`, like `aws kms create-key`, which puts every flag on its own line, a single flag included. Its `--query ... --output text` stays together on one line, as one output selector. Every create that runs only while its thing is missing, and every block that makes a thing while it is missing, is written as a `||` pair in the operator scripts and build-and-publish.sh, whether a describe or a string test like `[ -n "$x" ] ||` decides it and whether its second side is one command or a brace group. The pair breaks after the `||` even when the create takes no flags.

## Image structure

- The Containerfile's rootfs stage is COPY lines, then a single RUN line that marks /opt/scripts executable and runs setup.sh. Every other build-time mutation goes in setup.sh. The sealed stage only copies the signed UKI into /boot, because the UKI's command line carries the composefs digest of the flattened stage, and the digest covers every file outside /boot. build-and-publish.sh builds the sealed stage alone, from the localhost/flattened image it tagged. The flattened stage copies the rootfs stage into one layer, because over a multi-layer image the digest bootc install computes from container storage disagrees with the merged tree's on some directories' mode and mtime (bootc#2194).
- Other stages may RUN whatever fetches or builds an artifact, like the caddy-build and selinux-modules stages, or unpack one that build-and-publish.sh verified, like the stalwart stage, and the rootfs stage takes each artifact through `COPY --from`. The signed systemd-boot and UKI come from the build context's sealed/ directory instead, where seal.sh writes them between stages, because KMS makes each signature outside `podman build`. The site comes from the build context's site/ directory, where build-and-publish.sh writes the output of its `podman build` of the website's Containerfile, because that Containerfile is its own build. The stalwart stage takes its tarballs from the build context, because the base image has no gh to verify the attestations, and the release assets' bytes are the ones the attestations name.
- Every dnf step mounts rhel.repo and the entitlement certificate and key for its own RUN, so neither is stored in an image layer. The base image's dnf.conf empties installonlypkgs, so setup.sh's `dnf upgrade` replaces the kernel instead of installing a second one.
- Every file the image installs comes from a dedicated repository file COPY'd by the Containerfile. No heredocs or `printf > /path` for static file content inside setup.sh or boot scripts. Boot scripts may `printf` files they render from Parameter Store.
- First-boot PostgreSQL work (initdb and the SQL that needs it) is in bootstrap.sh, which boot-postgresql.sh calls until a bootstrap succeeds.

## Git

- Every commit goes to `main`, audit and fix passes included, and `main` stays the only branch.
- Run `git log -1` before any `git commit --amend`. The operator makes commits between turns, so HEAD may not be the commit you expect.
- Remove tracked files with `git rm`, which stages the removal.
- When one "commit" instruction covers several changes from the conversation, write one combined commit.

## Build

- Each build runs `podman build --layers=false` and builds every layer, because the layers are too small for caching to pay off.

## Operating the running VM

- Nothing logs into the VM, which has no sshd, no serial console login, and no user password. Every change to it, an /etc edit included, takes effect through a commit to the repository and an image update that applies it, so propose every fix as a commit.
- Inspect runtime state through the read-only console output: `aws ec2 get-console-output --latest --instance-id <id>`. Answer questions about deployed state from that output alone.
- bootc-fetch-apply-updates.timer fetches each update by itself, at the top of every hour, and reboots the VM to apply it. A reboot boots only an update the timer has already staged. To recover from bad state, reboot the whole VM with `aws ec2 reboot-instances`, whichever service failed.
- PostgreSQL and WebDAV are tailnet-only. Query PostgreSQL with `psql` and exercise WebDAV with `rclone <op> webdav:...`.

## Rulings

Each ruling below is settled. A later audit treats each as decided.

- Code comments state code-local facts. The README describes operator-facing behavior and points at files. The README keeps the security-posture mechanisms (secrets out of argv, the caddy_t domain, the pghash-group file, sigstore attachments, the base image's signature check, the sealed boot chain, the /var TPM policy) even where a code comment states them.
- AGENTS.md keeps the facts behind its rules even where the README or setup.sh states them. A fact that supports two rulings stands in both bullets, and a fact that two files' readers each need stands in a comment in both files, as the socket order does in caddy.socket and the Caddyfile.
- The 3-line cap on a comment covers every comment that documents the construct below it: a file header, a function, a statement, a Containerfile stage, or a configuration entry. A comment on one key inside a plan.jq object stays where it gives the reason for that setting's value, as the per-setting comments in postgresql.conf do.
- Prose and comments write "repository" and "directory" in full. Every mention of an ECR or CodeCommit repository carries its qualifier, a CodeCommit repository also names whose it is, this repository's or the website's, and an unqualified "the repository" means this git repository.
- The README's opening paragraph says that provision.sh puts every deployment-specific setting and secret the VM needs into Parameter Store. The Deployment & Configuration intro holds the one list of them.
- The README's FAQ holds recovery edge cases and operator how-tos, like the recovery from a bootstrap that ran with a mistyped password.
- service-restrictions.conf is the one set of restrictions every unit shares, linked into the `.service.d/` of every unit this repository provides, and holds the empty `CapabilityBoundingSet=`. Each unit states only its own differences. A unit that needs capabilities sets them in a `zz-capabilities.conf` drop-in, because the empty assignment resets the set, a drop-in parses after its unit file, and `zz-` sorts after service-restrictions.conf. The drop-in holds any `AmbientCapabilities=` the unit needs beside its `CapabilityBoundingSet=`, so one file states the unit's capabilities. Each drop-in's repository file carries its unit's name, as stalwart/stalwart-capabilities.conf and boot-config-capabilities.conf.
- bootstrap.sh runs initdb in a staging directory and renames it to `data` only after the SQL succeeds. boot-postgresql.sh tests for the hash file, which no unit removes from /run. /run is tmpfs, and every process that can read the file can read the same hash from pg_authid after bootstrap. boot-config.sh keeps the one first-boot test, and boot-config-capabilities.conf keeps CAP_DAC_READ_SEARCH for boot-config.service.
- A literal that a writer and its reader both name moves to one source only when a mismatch fails without an error. The PostgreSQL data directory is such a literal and is defined once, in pgdata.conf. The WireGuard port is another, because a mismatch uses DERP relays instead, and is defined once, in tailscale/wireguard-port.env. Pairs whose mismatch stops with an error keep their literals at both ends: Stalwart's loopback ports in plan.jq, the Caddyfile, and boot-tailscale.sh, the `bootc-sealed-vm` node name in boot-config.sh's `STALWART_PUBLIC_URL`, `/run/caddy/env`, `/run/caddy/mta-sts`, `169.254.169.254`, the `/bootc-vm/` parameter path in fetch-parameter.sh and build.env, the `bootc-vm` instance profile name in provision.sh's run-instances and infrastructure.yaml, and the hash file path.
- The build instance's Name tag fails without an error, because a filter that matches no instance leaves older builds running, so it is defined once, in build.env's `BUILD_INSTANCE_NAME`, which the stack takes as a parameter. The node name fails without an error in provision.sh, where an empty peer leaves the auth key's credential in place, so provision.sh, publish-tlsa.sh, and remove-boot-secrets.sh take it from build.env's `REPOSITORY`, and the scripts on the VM hardcode it.
- tailscaled.service and the nftables.service drop-in tailscale/nftables-wireguard-port.conf load wireguard-port.env with `EnvironmentFile=`, and provision.sh sources it. The drop-in passes `nft -D wireguard_port=...` in both `ExecStart=` and `ExecReload=`. Its `ExecReload=` loads the ruleset with `-f`, because nft 1.1.6 accepts `-D` only with `-f`. nftables.conf's opening `flush ruleset` makes each reload replace the loaded ruleset.

The comment above `hba_file` holds the fact that initdb's pg_hba.conf trusts every local connection, because the setting protects both servers. The data directory keeps initdb's unused configuration files.

- postgresql.conf's sizing comment names the gp3 volume beside m9g.medium, because random_page_cost depends on the disk, not the instance type.
- The security group and nftables both hold the inbound allowlist, and bootstrap.sql's CONNECT revoke and pg_hba.conf both confine `experiments` to its own database. Each pair is two enforcement points.
- When a directory already confines access to the service's user or to the reading group, a file mode inside it is redundant, not a second enforcement point like the two pairs above. caddy carries no `UMask=` inside its 0700 /var/lib/caddy, and boot-config.sh writes the hash file without a chmod inside the 0750 root:pghash `RuntimeDirectory=`.

- The AWS resources keep the `bootc-` prefix (the bootc stack, bootc-ip, bootc-build, bootc-vm, alias/bootc-secureboot, /bootc-build/, /bootc-vm/) as an abbreviation of the repository's name, bootc-sealed-vm, not a second name. - Every `COPY --from` in the rootfs stage carries `--chown=0:0`. A new one needs the flag, because `--chown=0:0` is the only build step that makes root own files from another stage or image. The flattened stage's copy of the rootfs stage carries no `--chown`, so every file keeps its owner.
- A tmpfiles snippet's repository name matches its installed basename.
- `bootc container lint` is the last line of setup.sh, so the build fails on a lint error.
- Every `podman run` in operator-tools.sh uses `--log-driver=none`, and every aws call that carries a secret reads it from a `file://` path on /dev/fd, or on the entitlement's tmpfs. The AWS CLI rejects `--cli-input-json` from a pipe (2.42.1), so a secret goes in as one option's value. The IMDS session token counts as a secret, and aws-api.sh and build-and-publish.sh pass it to curl as a `header` line of a configuration on stdin.
- The secrets-out-of-argv posture covers every script, every container, and every operator command in the README that handles a secret. The Access psql URI therefore names no password, and psql prompts for it. Each of build-and-publish.sh's `podman login` calls reads its token through `--password-stdin`, and provision.sh's hashers read each password from stdin, inside the operator-tools container.
- A secret with one consumer reaches it through a pipe under pipefail and takes no shell variable, as the IMDS token does in build-and-publish.sh, both tokens do in tailscale/apply-policy.sh, and the certificate signing key and both password hashes do in provision.sh. A secret with several uses stays an unexported variable until its script exits, as entitlement.sh's `build_secret` does, and no script runs `unset`. The README's token command reads its token inside a subshell, which ends the variable. A pipe runs its last stage whatever the earlier ones did, so a failed token exchange in apply-policy.sh still posts the policy file once, without a token, before pipefail stops the script. provision.sh pipes the PostgreSQL hash into its own `aws ssm put-parameter`, which reads it as `file:///dev/fd/0`.
- The entitlement registration is the one exception to the secrets-out-of-argv posture, because subscription-manager must reach Red Hat and reads a password only from a terminal: it prompts for the Red Hat login itself and writes the certificate and key to a tmpfs on /etc/pki/entitlement, and entitlement.sh writes the stored pair to a tmpfs under $XDG_RUNTIME_DIR for the operator-tools stage's dnf step.
- A line that states a tool's built-in default stays, unless it repeats a value the repository sets elsewhere. A unit omits a `Group=` that would repeat its user's primary group, which setup.sh's `useradd -g` sets. tailscaled.service passes no `--socket=`, because the built-in /var/run/tailscale/tailscaled.sock, which the CLI also uses, lies in the unit's `RuntimeDirectory=tailscale`. tailscaled's `--port=${WIREGUARD_PORT}` stays, because its built-in default is 0, a random port (tailscaled 1.104.4 `--help`), and the security group and nftables need a fixed one. tailscaled's `--state=${STATE_DIRECTORY}/tailscaled.state` stays, since it names no literal.

- run-as-postgres.conf holds the `User=` and `ReadWritePaths=` both PostgreSQL units share and links in beside service-restrictions.conf. run-as-stalwart.conf does the same for stalwart.service and stalwart-apply.service.

With the rule, PostgreSQL runs confined in `postgresql_t` under NNP in enforcing mode. Scripts under /opt run as `unconfined_service_t`, which `init_t` may enter under NNP, so boot-postgresql needs no rule. postgresql_local.fc labels only `postgres`, `initdb`, and `pg_ctl`, the PGDG binaries whose /usr/bin counterparts RHEL's policy labels `postgresql_exec_t`. The build checks no signature on the release binary.

The rule also covers a process substitution `<(...)` that runs an external command. It binds the README's code blocks. A `$(<file)` runs no command and goes inline at its one reference, as build-and-publish.sh's `--uefi-data` value does. It covers every substitution that runs a command, a polling loop's test and a site whose next command would stop with an error included, so a `dig` that gets no reply stops reserve-address.sh. ecr-login.sh pipes the login into jq under pipefail, so a failed call stops the unit and leaves an empty auth.json, which the next hour's login rewrites. fetch-parameter.sh takes the empty key as its request to list the keys, since Parameter Store has no empty key.

- The README's "Why bootc" names the five signed links (base image, packages, Stalwart's server and CLI attestations, Caddy's release tag, published image), plus each build's signature on the boot chain, and counts them, because the spam rule set carries no signature and the build checks none on the site's base images. The comparison holds once bootc#2629 reaches RHEL, which Digest Enforcement states.

It sets `RandomizedDelaySec=0`, because the stock two-hour delay spreads many VMs' load on the registry and this is one VM. `AccuracySec=1us` replaces the default one-minute window in which systemd coalesces wake-ups, so a fetch fires at the top of each hour. infrastructure.yaml's `bootc-build-daily` rule starts the daily build at 23:30 UTC, so the 00:00 fetch finds its image. The file is separate from the composefs drop-in, which the Containerfile also copies into the .service's drop-in directory, where a `[Timer]` section draws a warning.

Stalwart's recovery admin takes only plaintext, and the secret exists only in the two processes' environments for that run. stalwart-apply.service allows any IP address, because creating the ACME provider registers its Let's Encrypt account during the apply. nftables and the security group keep the recovery port closed.

Stalwart serves its built-in WebUI while no Application object exists, and its `allowedEndpoints` exempts loopback, where every request arrives.

It also sets the selector as a parameter, so the plan and the DNS record take one selector from one place. The mailbox sends as the primary domain alone, so only that domain publishes the key and an SPF record naming Forward Email's servers, and each alias domain publishes `v=spf1 -all`. Stalwart 1.1.1 would sign an alias domain's mail with the primary domain as `d=` (checked 2026-11-23), which fails DMARC alignment for the alias.
